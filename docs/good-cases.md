# 真实视频回归案例

这里保存值得重复验证的真实输入，包含 good case 的成功路径、同一输入的失败记录和复测要点。它是手动验收清单，不会被 pytest 自动下载或转写。

“good case”表示这个输入能覆盖重要场景，而且已有可核验的成功结果；不表示每次请求都成功，也不表示识别正文完全正确。下列日期是历史验证日期，平台内容和字幕后来可能变化。

## 测试用例保存在哪里

| 内容 | 保存位置 | 是否进入 Git |
| --- | --- | --- |
| 自动化回归代码 | `tests/test_*.py`；样例字典、假下载器和假识别结果主要写在函数或 fixture 中 | 是 |
| 自动化测试生成的文件 | pytest 的 `tmp_path`，用于模拟 WAV、文字稿、SQLite 等 | 否，运行时临时生成 |
| 真实链接、测试场景、复测步骤、成功与失败摘要 | 本文；平台说明保留详细历史记录 | 是 |
| 视频、音频、完整转写稿、配置、原始日志和截图包 | 本机 `data/`、`.v2t/` | 否，已被 `.gitignore` 忽略 |
| ASR 准确率评测输入与结果 | 本机 `bench/`，见 [评测方法](benchmark.md) | 否 |

真实样本可以用于复测下载、模型加载、长音频输出、缓存和导出。评测 CER 还需要与音频区间严格对应、逐句核对的参考稿；AI 润色或补充技术条件的正文不能直接当作逐字参考答案。

### 复测步骤

网络链路复测使用新的独立工作区，例如：

```bash
uv run video2text tx "https://www.bilibili.com/video/BV1o4p568Etd/" \
  --workspace .v2t/manual-cases/redis-new-download-YYYYMMDD \
  --provider faster-whisper --model large-v3-turbo --force-asr
```

这是建议的复测命令，不是对原始运行参数的还原。选择 `--force-asr` 是为了固定识别场景，普通字幕优先需要另跑一轮；新的工作区才能检查新下载，复用同一工作区通常会命中音频缓存。

复测时检查并记录：

1. 下载、ffmpeg、模型加载和转写分别是否成功；输出是否包含课程结尾。
2. segments 的时间顺序、开头及结尾位置；术语提示有无改善，同时有没有带偏其他文字。
3. 同一工作区重复强制 ASR 时是否复用 WAV、跳过下载和抽音频，并独立保存新稿；1804 是历史片段数，不要求未来模型逐次完全一致。
4. TXT / Markdown / SRT 与所选原稿是否一致；校订或 AI 优化稿不借用原稿时间戳。

配图回归：用一个独立工作区启动 Web，在新建页粘贴本地 Redis MP4 的绝对路径，勾选「为文字稿配图」并提交。打开原稿，对照 35 页参考清单逐图复核；再从详情页下载图文包，把解压后的 Markdown 阅读段和 JPEG 同网页逐项比较。

本次配图实测运行在 macOS 26.4.1 / arm64，faster-whisper 1.2.1、FFmpeg 9.0.2。Chrome 从新建页提交本地 MP4，模型从本机缓存读取（`HF_HUB_OFFLINE=1`），未访问 B 站；默认 ASR 模型配置没有改变。

本次配图实测使用了独立的 `data/redis-illustrated-mvp/` 工作区。服务未运行时，在仓库根目录执行 `uv run video2text ui --workspace "$PWD/data/redis-illustrated-mvp" --port 8876` 即可查看这次的任务和文字稿。

历史材料位于 `data/downloads/BV1o4p568Etd.mp4`、`data/metadata/` 中同标题 JSON、`data/exports/Redis-完整课程-校订稿.txt`、`data/exports/Redis-校订说明.md`、`data/exports/Redis-关键帧图文样稿/`。这些位置只用于寻找当前本机证据，不要求其他 checkout 拥有相同文件、视频库编号或缓存文件名。

## youtube-zoo

- 链接：<https://www.youtube.com/watch?v=jNQXAC9IVRw>；约 19 秒，适合低成本检查字幕与音频两条路径。
- 最近详细记录：[2026-10-23 真实 CLI 复测](platforms/youtube.md#2026-10-23-真实-cli-复测)，代码 `9eaf8a5`；独立工作区、本机代理、`large-v3-turbo`、CPU int8、语言 `auto`。
- 当日字幕路径成功获取 6 段英文字幕，跳过媒体和 ASR，入库并导出 txt/plain/md/srt，耗时 5.95 秒。
- 当日使用已经缓存的 WAV，连续两次强制 ASR 得到 5 段英文转写、独立新稿和四种导出；WAV 哈希及修改时间不变，耗时 15.20 / 14.07 秒。
- 同时保留失败：首次强制 ASR 下载和 ffmpeg 成功，但 `HF_HUB_OFFLINE=1` 下模型缓存加载失败；立即复用缓存仍失败。后来新工作区的两次重新下载都因 SSL EOF 失败。后续缓存 ASR 成功不覆盖这些失败。

复测先用新工作区跑普通转写；再分别跑强制 ASR 和缓存复用，检查下载阶段、WAV 哈希与修改时间、新稿独立保存及导出。当前字幕段数和历史耗时只作对照，不是固定通过门槛。ASR 的 `faster_whisper.language` 应设为 `auto`；代理及依赖条件见 [YouTube 平台说明](platforms/youtube.md)。常规复测不要求开启 `HF_HUB_OFFLINE`。

## 怎样新增或更新案例

优先保存能覆盖独特场景、输入相对稳定、复测成本可接受的案例。每条记录至少包含：

- 稳定案例 ID、公开规范链接、视频 ID、标题及场景。
- 验证日期、代码提交号、引擎/模型/语言、提示词、网络/代理及依赖条件；没保存的信息明确写“未记录”。
- 新下载、音频缓存复用或本地文件复用的范围；成功结果和失败阶段分别记录。
- 输出完整性、主要术语、导出和版本检查点；历史段数、耗时与正式验收门槛分开。
- 本机证据位置、已知误词及未验收项。追加新轮次，保留旧失败，不能只留下成功结果。

Git 保存这类小文本记录；将来需要确定性离线回归时，可以新增经过裁剪和脱敏的 JSON、segments 或人工逐句核对的小段参考稿，并由测试显式读取。实际媒体、完整课程稿、签名下载地址、Cookie、密钥、个人配置和原始日志不随案例登记提交。

准确率评测按 [benchmark.md](benchmark.md) 准备音频及逐句参考稿；如果只是原稿到导出的格式测试，使用合成 segments 即可，不必复制整段课程。
